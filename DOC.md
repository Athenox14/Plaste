## File sharing API

Owner routes (require `Authorization: Bearer <token>`; caller must own the resource, or be admin):

| Method | Path | Body / query | Response |
| --- | --- | --- | --- |
| POST | `/shares` | `{resource_type: "file"\|"folder", resource_id: int, permission: "read"\|"write"\|"comment", password?: string, expires_at?: rfc3339}` | `{id, share_token, permission, expires_at}` |
| GET | `/shares` | — | `[{id, share_token, resource_type, resource_id, permission, expires_at, created_at, password_protected, view_count, download_count, last_access_at}]` |
| DELETE | `/shares/{id}` | — | `204`, link stops working immediately |

The public link is `/public/shares/{share_token}`. `share_token` is 128 bits of CSPRNG
randomness, base64url, 22 chars. `expires_at` must parse as rfc3339 or the request is `400`.

Public routes (NO authentication — anyone holding the link):

| Method | Path | Password | Query | Response |
| --- | --- | --- | --- | --- |
| GET | `/public/shares/{share_token}` | `X-Share-Password` header | — | file: `{kind: "file", name, size, content_type}` · folder: `{kind: "folder", name, children: [name]}` |
| GET | `/public/shares/{share_token}/download` | `X-Share-Password` header **or** `?t=<ticket>` | `t?` | streamed file bytes (files only) |

The password is only ever accepted in the `X-Share-Password` header, never in the query
string: a URL ends up in the reverse proxy's access log, the browser's history and address bar,
and in the `Referer` of any outbound navigation. There is no `?password=` fallback.

A **download ticket** exists because a download is a `GET` the browser performs, which cannot
carry a header. A ticket is `base64url(exp "." base64url(blake3::keyed_hash(key, token "." exp)))`,
lives **120 seconds**, is bound to one share token, and is signed with a BLAKE3-derived subkey
of the existing master key (`PLASTE_DATA_DIR/master_keys.json`) — so it survives restarts, needs
no new config, and cannot decrypt anything. A ticket replaces the *password check* only: the
share row is still re-read and re-validated on every download, so a revoked or expired share
stops downloading at once even with a valid ticket in hand.

Public status codes: `404` unknown or revoked token · `410` expired · `401` password missing
or wrong · `429` too many password attempts (5, then 1 per 12s, per share token) ·
`400` download requested on a folder share.

Notes for clients:
- Expiry, revocation and password are re-checked on **every** request; a successful password
  check issues no cookie or session, so revoking a share takes effect at once.
- Downloads always come back as `Content-Type: application/octet-stream` with
  `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, regardless of the
  file's real type — user-uploaded HTML must not execute on this origin. Use `content_type`
  from the metadata route for display purposes only.
- Statistics are aggregate only (counts plus last access time). No per-visitor data — no IP,
  user agent or visit history — is recorded.

## Human-readable share page

`GET /s/{share_token}` (plus `POST /s/{share_token}` for the password form) renders an HTML
landing page for the same share, for a person who clicked the link in a message rather than a programmatic client. It
delegates every validity check to the exact same `load_valid_share` used by the JSON routes
above, so revocation/expiry/password/rate-limit behave identically — this route is purely a
different rendering of that same state, not a second source of truth.

- Unknown or revoked token → one shared message ("this link doesn't exist or is no longer
  valid"), same wording for both cases, `404`.
- Expired → distinct message, `410`.
- Password-protected → an inline `<form method="post">` posting back to the same URL with the
  password in the request **body**; wrong password shows an error, `401`. The rate limit is keyed
  on the share token, so the POST consumes the same brute-force budget.
- Too many password attempts → distinct message, `429`.
- On success: escaped file name, human-readable size, and a download button pointing at the
  existing `/public/shares/{share_token}/download` route (carrying `?t=<ticket>` if the share is
  protected — never the password) — no separate download path exists on this page.
- Folder shares resolve but show a short notice instead of a browser, since the download route
  only serves files.
- Sets `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, so a page holding a
  download ticket is not cached by a proxy and the ticket does not leak in a `Referer`.
- Sets a restrictive `Content-Security-Policy` (`default-src 'none'`) and `nosniff`; the file
  name is HTML-escaped before being placed in the page, since it is chosen by whoever uploaded
  the file.
